# 적용 예시 — 부동산 계산 앱 온보딩 (한 가지 사례)

입력을 어떻게 채웠고 무엇이 나왔는지. 방법은 도메인 무관 — 모양만 참고.

## 입력
- **페르소나**: k-persona로 인-마켓 20명(수도권 기혼 매수기 + 미혼 입문 + 45-55 + 지방 광역시).
  결혼·가구·연령·지역 필터로 근사, `--seed` 고정.
- **도메인 한 줄**: "주거(매수·전세·매도·보유) 의사결정".
- **발견경로 레퍼런스**: 인스타 광고("영끌 전에 내 연봉으로 살 수 있는 집"), 필수앱 바이럴,
  쓰레드 입소문, 지인 카톡, 유튜버 멘트("DSR 헷갈리면 미리 돌려봐라").
- **화면+분기**: 에뮬레이터 실구동 캡처 → 01_intent → (살집)04_target→05_rec_buy / (전월세)03_rec_lease
  / (매도)07 / (보유)08 / (둘러보기)06.

## 나온 것
- **핵심**: 같은 추천 화면이 *경로*에 따라 갈렸다. 인스타 유입("내 연봉으로 살 수 있는 집")은 주
  카드 "얼마까지 살 수 있나요?"와 일치 → 충족. 유튜버 유입("DSR·한도부터")은 그 화면이 "예산 먼저"를
  밀어 한도를 보조로 강등 → 배신. 경로→기대를 모델링한 2단계라서 잡힌 발견.
- 검증된 화면 마찰: 갈아타기 칩 부재 / target "안 정함"vs"모르겠음" 변별 불가 / 전세 추천 '원리금' 오독.

## 가짜 발견 교정 (정직성)
집계가 P0로 올린 "대출 한도 카드 데드엔드(유일 이탈)"는 버그가 아니었다. 정적 스크린샷만 줘서
페르소나가 "탭했더니 반응 없음"을 *상상*한 것 — 실제 코드는 정상 라우팅. 인터랙션 주장은 코드/실구동
교차확인.
