# 글을 남길 때: 독자에게 필요한 최종 상태만 적으세요

스킬 문서, 스펙 문서, PRD, 보고서처럼 다시 읽힐 글과 사용자에게 전달할 산출물은 그 자체로 완결되어야 합니다. 독자는 제작 과정이 아니라 현재 유효한 내용과 자신에게 필요한 행동을 읽어야 합니다.

대화와 피드백은 산출물을 만드는 데 사용하고, 산출물에는 그 과정을 거쳐 도달한 결과를 남깁니다. 받은 지시를 설명하는 대신 문서의 구조, 표현, 범위, 가정과 기본값에 반영하세요.

## 제작 맥락과 독자용 내용을 구분하세요

산출물에 들어갈 내용을 다음 세 범주로 분류합니다.

1. **독자에게 필요한 내용**: 문서의 목적을 달성하고 결과물을 올바르게 이해하거나 사용하는 데 필요한 정보입니다. 산출물에 직접 적습니다.
2. **제작 지침**: 작성자에게 주어진 피드백, 제약, 예시와 교정 신호입니다. 산출물의 구성과 표현에 반영한 뒤 제작 과정에서 소진합니다.
3. **제작 과정의 잔여물**: 대화 이력, 중간 판단, 폐기한 접근법과 수정 경위처럼 독자에게 필요하지 않은 정보입니다. 산출물에서 제거합니다.

피드백은 작성자인 당신을 대상으로 하고, 산출물은 독자를 대상으로 합니다. 두 대상이 다르다는 사실을 기준으로 내용을 판별하세요.

## 도달할 최종 상태를 직접 서술하세요

부정형 교정은 바람직한 최종 상태를 찾는 입력입니다. 교정에 등장한 폐기 대상과 변경 이력을 다시 설명하지 말고, 교정이 가리키는 현재의 기준과 행동을 직접 적습니다.

- **대조 정의**: “기준이 X면 안 되고 Y여야 한다”에서 “기준은 Y다”를 추출합니다.
- **금지**: “A하지 마라”에서 A를 대체할 바람직한 행동 B를 찾아 “B하라”라고 적습니다.
- **정체성 교정**: “이 문서는 규칙 나열이 아니다”에서 문서의 실제 역할을 찾아 “이 문서는 사고방식을 다룬다”라고 선언합니다.
- **변경 이력**: 이전 표현을 제거하라는 피드백을 받으면 현재 유효한 표현만 남깁니다.
- **폐기 용어**: 버리기로 한 개념은 새로운 독자가 알 필요가 없으므로 현재 기준을 설명하는 어휘로 교체합니다.

폐기된 개념을 다시 언급하면 독자는 그 개념을 먼저 이해한 뒤 버려야 합니다. 목표 상태를 직접 서술하면 독자는 현재 유효한 내용만 읽고 바로 행동할 수 있습니다.

## 제작 과정의 흔적을 정리하세요

다음 내용은 독자에게 필요한지 판별한 뒤, 필요하지 않다면 자연스러운 최종 문장으로 바꾸거나 제거합니다.

- 사용자의 프롬프트와 대화 이력
- 중간 추론과 검토 과정
- 도구 선택과 구현 방식
- 제작 중 적용한 제약과 배제한 접근법
- 의도를 전달하기 위해 제공된 임시 예시
- 수정 전 표현과 교정 경위
- “요청에 따라”, “요구사항을 만족하기 위해” 같은 제작 과정 설명
- 여러 차례 수정하면서 생긴 용어, 어조와 전제의 불일치

제약은 일반적으로 결과물의 설계로 표현합니다. 예를 들어 공유 방법이 Google Drive로 정해졌다면, 배제한 도구를 나열하는 대신 Google Drive를 사용하는 절차를 직접 안내합니다.

대화에서 사용한 예시는 의도, 독자, 추상화 수준과 어조를 파악하는 자료입니다. 산출물 자체에 필요한 예시만 남기고, 의도 전달용 예시가 문서의 주제로 바뀌지 않게 합니다.

## 작성 및 수정 절차

1. **독자와 목적을 확정합니다.** 이 글을 읽는 사람이 무엇을 이해하거나 수행해야 하는지 한 문장으로 적습니다.
2. **입력 내용을 분류합니다.** 각 지시와 정보를 독자용 내용, 제작 지침, 제작 과정의 잔여물로 나눕니다.
3. **바람직한 최종 상태를 추출합니다.** 부정형 교정과 제약을 현재 유효한 기준, 행동, 구조와 표현으로 변환합니다.
4. **독자용 문장으로 작성합니다.** 제작 지침은 산출물에 설명하지 않고 문서의 구성과 표현에 적용합니다.
5. **제작 흔적을 제거합니다.** 프롬프트, 대화, 수정 경위, 도구와 폐기한 접근법이 불필요하게 노출되는 문장을 정리합니다.
6. **하나의 문서로 다시 읽습니다.** 제목, 용어, 어조, 전제와 설명 수준을 통일하고 여러 차례 수정한 흔적을 없앱니다.
7. **산출물 자체를 전달합니다.** 별도의 작업 보고가 필요하지 않다면 완성된 결과물만 출력합니다.

설명보다 수정을 우선하세요. “이 부분을 정리했다”라고 덧붙이는 대신 해당 부분을 자연스러운 최종 형태로 고칩니다.

## 독자에게 필요한 부정과 제약은 남기세요

부정, 대조와 제작 제약도 독자가 결과물을 올바르게 이해하고 사용하는 데 필요하다면 산출물의 내용입니다.

- **안전 및 위험 경고**: 특정 행동이 데이터 손실이나 보안 문제를 일으키는 경우
- **실제 사용 조건**: 호환성, 지원 범위, 필수 선행 조건과 운영상의 한계
- **독자가 흔히 품는 오해의 교정**: 독자가 자연스럽게 잘못 이해할 가능성이 높은 경우
- **교육용 안티패턴**: 잘못된 사례와 올바른 사례의 비교 자체가 학습 목표인 경우

판단이 어려우면 해당 문장을 지웠을 때 독자가 중요한 정보나 올바른 행동 기준을 잃는지 확인합니다. 잃는 정보가 있다면 남기고, 제작 과정만 사라진다면 제거합니다.

## 최종 검증

산출물을 전달하기 전에 다음 항목을 확인합니다.

1. 대화를 보지 않은 독자도 문서의 목적과 내용을 이해할 수 있습니까?
2. 모든 문장이 현재 유효한 기준과 행동을 직접 설명합니까?
3. 작성 방식과 수정 이유를 불필요하게 해설하는 문장이 남아 있습니까?
4. 프롬프트, 대화, 도구, 배제한 접근법과 중간 판단이 노출되어 있습니까?
5. 의도 전달용 예시가 산출물의 내용으로 잘못 들어갔습니까?
6. “아니라”, “말고”, “대신”, “예전에는”, “기존에는” 같은 표현이 독자에게 실제로 필요한 대조나 이력을 전달합니까?
7. 제목, 용어, 어조, 전제와 설명 수준이 문서 전체에서 일관됩니까?
8. 경고, 제약과 예외는 독자가 알아야 할 정보만 담고 있습니까?
9. 산출물이 하나의 목적과 목소리를 가진 독립적인 결과물로 읽힙니까?

## 출력 규칙

사용자가 문서의 작성, 수정이나 검수를 요청하면 완성된 산출물 자체를 먼저 출력합니다. 제작 과정과 정리 작업을 설명하는 머리말은 붙이지 않습니다.

사용자가 변경 요약도 요청했다면 산출물을 먼저 제시하고, 변경 요약은 그 뒤에 분리하여 작성합니다.
